# Deploy handover notes

This file is for whoever stands OpsPilot up outside a developer's laptop. It
covers what's already automated, what still needs a decision from you, and
the defaults that are safe for local dev but **not** safe to expose publicly
as-is.

## What's in the box

`docker compose up -d --build` now brings up all five services as one unit:

| service | what it is | restart policy | healthcheck |
|---|---|---|---|
| `postgres` | traces / HITL / eval history | `unless-stopped` | `pg_isready` |
| `redis` | sessions, rate limiting, idempotency, budget counters | `unless-stopped` | `redis-cli ping` |
| `chromadb` | vector store for the knowledge base | `unless-stopped` | heartbeat endpoint |
| `mock-order-service` | **fake** order backend, 500 seeded orders (`random.seed(42)`), resets on every restart | `unless-stopped` | `/health` |
| `app` | the actual OpsPilot API (port 8000) | `unless-stopped` | `/api/v1/health` |

`app` waits on the other four being healthy (`depends_on: condition:
service_healthy`) before it starts, and its `DATABASE_URL`/`REDIS_URL`/
`CHROMA_HOST`/`ORDER_SERVICE_URL` are overridden in `docker-compose.yml` to
use the in-network service names — the values in `.env` (`localhost:...`) are
only correct for running things directly on the host, not from inside a
container.

Container images for `app` and `mock-order-service` are also built and
pushed to GHCR automatically on every merge to `main`
(`.github/workflows/docker_build_push.yml`) as
`ghcr.io/<org>/<repo>-app:latest` and `ghcr.io/<org>/<repo>-mock-order-service:latest`
— pull those instead of building on the deploy box if you'd rather not build
there.

## First deploy, step by step

```bash
cp .env.example .env      # then fill in the required values below
docker compose up -d --build
alembic upgrade head                        # creates traces/hitl/eval_runs tables
python scripts/ingest_knowledge.py --reset  # embeds the knowledge base into ChromaDB
curl http://localhost:8000/api/v1/health    # expect {"status":"healthy", ...}
```

`alembic upgrade head` and the ingest script both talk to Postgres/ChromaDB
over the ports exposed on `localhost` (5432 / 8100), so run them from the
host, not inside a container.

## Env vars — what's required vs optional

Required (the app degrades to "broken" without these):
- `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_VERSION`
- `AZURE_DEPLOYMENT_GPT54`, `AZURE_DEPLOYMENT_GPT54_MINI`,
  `AZURE_DEPLOYMENT_GPT4O`, `AZURE_DEPLOYMENT_EMBEDDING` — these are your
  Azure **deployment names**, not model names; they must already exist in
  your Azure OpenAI resource.

Optional — the app starts fine without these, just with a feature quietly
disabled:
- `SLACK_WEBHOOK_URL` — HITL/medium-risk notifications fall back to logs only
- `JIRA_BASE_URL` / `JIRA_EMAIL` / `JIRA_API_TOKEN` / `JIRA_PROJECT_KEY` — the
  Jira tool becomes a no-op without these

Everything else in `.env.example` (retrieval/session/budget/HITL tuning
knobs) already has a working default.

## Security defaults you MUST change before this is reachable from the internet

Two settings in `.env.example` are dev-only defaults, not oversights:

- `OPSPILOT_API_KEY=""` — empty means **auth is off**, anyone can call the
  API. Set a real value.
- `CORS_ALLOW_ORIGINS=["*"]` — any website can call this API from a browser.
  Set it to your actual frontend's origin(s).

Neither of these is enforced by the app — nothing will warn you if you go
live with the defaults, so treat this as a manual checklist item.

## Network exposure

Only ports **80/443** (behind a reverse proxy — Caddy or Nginx, not included
here) should be reachable from the public internet. `docker-compose.yml`
currently publishes 5432 (Postgres), 6379 (Redis), 8100 (ChromaDB), and 8001
(mock order service) on the host for local dev/ingest convenience — on a
public box, firewall those off from the outside world (e.g. `ufw deny` from
any source except `localhost`), or bind them to `127.0.0.1` in
`docker-compose.yml` instead of `0.0.0.0`.

No TLS termination or reverse proxy is set up in this repo — that's the one
piece that's genuinely infra-specific and left for you to add.

## Backups

`scripts/backup.sh` dumps Postgres (`pg_dump`) and snapshots the ChromaDB
data directory into `backups/<timestamp>/`, keeping the last 14. Nothing
calls it automatically — wire it into cron, e.g.:

```cron
0 3 * * * cd /path/to/opspilot && ./scripts/backup.sh >> backups/backup.log 2>&1
```

Without this, losing the disk loses all trace/HITL history and the embedded
knowledge base (the knowledge base can be regenerated by re-running the
ingest script; trace/HITL history cannot).

## Sizing (rough starting point, not measured under load)

Postgres + Redis + ChromaDB + the app together are light at rest; ChromaDB's
memory use grows with knowledge base size (currently ~90 chunks — trivial).
2 vCPU / 4GB RAM is a reasonable starting point for a low-traffic deploy;
watch `docker stats` after a few days of real traffic and resize from there.
No load testing has been done against this stack.

## Known limitation: the order backend is fake

`mock-order-service` is seeded demo data for evals/testing, not a real
integration — it resets to the same 500 orders on every container restart.
Going live against real customers requires swapping it for ShopEasy's actual
order system (same `ORDER_SERVICE_URL` contract, different implementation
behind it). As shipped, this stack is a fully working **demo**, not a
production order-processing integration.
